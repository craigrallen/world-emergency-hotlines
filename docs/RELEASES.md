# Public release changelog

The machine-readable source for this changelog is [`releases.json`](releases.json). It is append-only and records only factual, already-delivered public milestones. It is not an incident log, deployment ledger, availability report, or semantic-version promise.

## Entry contract

Each entry has a stable `id`, valid ISO `date`, short `title`, and a non-empty list of factual `facts`. Entries are newest first; IDs must not duplicate, while multiple milestones may share a date. Automated verification checks the schema, ordering, duplicate IDs, conservative claims, and that the public `/releases` page renders directly from the JSON source. Add an entry only after the capability is public in repository history; do not generate entries from commit subjects without review.

The current seeded milestones are rendered at <https://worldhotlines.org/releases>.

## Dataset changes and feeds

`dataset-releases.json` is the separately reviewed dataset registry. Every entry references a complete metadata-only snapshot in `dataset-release-snapshots/` by its exact-byte SHA-256. Schema 2 snapshots contain stable record IDs, canonical record hashes, non-empty per-record field-hash maps (including the exact `id` hash), and non-empty hashes for every country-level field except `hotlines`. This represents empty countries and covers `country`, `alpha-2`, `alpha-3`, `region`, `subregion`, `general_emergency`, `notes`, and future country fields without publishing their before/after values. Every delta is recomputed from consecutive tracked snapshots. The latest snapshot and dataset identity must match the exact `hotlines.json` bytes or the build fails.

PR #85 created the only schema-1 baseline before any real delta existed. The schema-2 migration deterministically replaces that one incomplete baseline snapshot and registry entry. Trusted-base CI permits the replacement only when the base registry bytes, baseline entry/hash, and snapshot bytes match the documented PR #85 fingerprints, the base has exactly one entry, and `hotlines.json` still has dataset identity `sha256:e893c9f6b0afcc57832054547002c826e80b5387e544b4cf6909afc9424dde3a`. There is no generic history-rewrite switch. After this migration, every prior registry entry and snapshot must remain an exact unchanged prefix.

Append a reviewed release with `cd web && npm run release:dataset:candidate -- --id <lowercase-slug> --date <YYYY-MM-DD> --title <title> --summary <summary>`. All arguments are required. The command validates real, repository-contained `docs` and snapshot directories, rejects symlink components/targets and unchanged dataset identities, refuses duplicate IDs, creates the complete snapshot, and computes the delta from consecutive snapshots. Ordinary builds never create candidates. Review the snapshot and registry append together.

Candidate publication is a recoverable two-file transaction, not a globally atomic filesystem operation. It exclusively stages both files and a closed, hash-bound marker under the fixed `docs/.dataset-release-transaction/` location, validates both staged representations, then installs the snapshot followed by the registry with file/directory syncs where the platform supports them. On startup, a validated incomplete transaction is removed safely; if the registry already references the marker's exact snapshot, only transaction cleanup is completed. Recovery never deletes marker-supplied arbitrary paths. PR CI still compares the trusted-base registry and snapshots as an unchanged prefix. Local verification supplies internal SHA-256 hash-chain consistency and tamper evidence, not a signature, publisher authentication, or external cryptographic anchor.

Objects are recursively key-sorted before record hashing. Arrays are preserved in source order: contact methods, sources, languages, and other arrays may carry display, priority, or provenance meaning. Registry, snapshot, change, feed, release-identity input, and artifact enumeration ordering uses the `utf16Compare` contract: JavaScript lexicographic UTF-16 code-unit order, never locale collation. BMP/non-BMP fixtures pin the behavior. Builds do not consult Git, GitHub, the network, filesystem enumeration order, locale, untracked files, wall clock, or subscriber/activity data for release history. Only the PR append-only verifier reads the explicitly supplied trusted base Git ref.

Public deterministic endpoints are `/release/v1/changes.json`, `/release/v1/changes/latest.json`, `/feeds/releases.json` (JSON Feed 1.1), `/feeds/releases.rss` (RSS 2.0), and `/feeds/releases.atom` (Atom 1.0). Feeds combine reviewed `releases.json` milestones and dataset-registry releases, newest first. Same-date ties sort by entry kind (`dataset`, then `milestone`) and stable source ID using UTF-16 code-unit order. Dates are represented at `00:00:00Z`; no build time is substituted. Stable entry IDs live under `https://worldhotlines.org/releases/{kind}/{id}`.

Change artifacts publish stable hotline IDs, country codes/names, change types, sorted changed field names, and counts only. They never publish raw before/after record or country-field values. Record additions, removals, content modifications, and country moves remain record events. Country additions, removals (including empty countries), renames, and any country-field modification are one explicit `country_metadata_changes` event with `added`, `removed`, or `modified` type. A country rename does not inflate its hotline records. A pure record move has no misleading empty `changed_fields`; a move with record-content edits includes only those edited fields. Country summaries separate record movement and all three metadata event types; strict validation recomputes the entire stored delta from its consecutive snapshots.

These files document release-integrity mechanics only; they do not make a licensing or open-data representation.
