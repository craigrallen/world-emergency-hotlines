# Public release changelog

The machine-readable source for this changelog is [`releases.json`](releases.json). It is append-only and records only factual, already-delivered public milestones. It is not an incident log, deployment ledger, availability report, or semantic-version promise.

## Entry contract

Each entry has a stable `id`, valid ISO `date`, short `title`, and a non-empty list of factual `facts`. Entries are newest first; IDs must not duplicate, while multiple milestones may share a date. Automated verification checks the schema, ordering, duplicate IDs, conservative claims, and that the public `/releases` page renders directly from the JSON source. Add an entry only after the capability is public in repository history; do not generate entries from commit subjects without review.

The current seeded milestones are rendered at <https://worldhotlines.org/releases>.

## Dataset changes and feeds

`dataset-releases.json` is the separately reviewed dataset registry. Every entry references a complete metadata-only snapshot in `dataset-release-snapshots/` by its exact-byte SHA-256. Snapshots contain stable IDs, country names/codes, canonical record hashes, and per-field hashes sorted by Unicode scalar value, but no raw hotline values. Consequently every delta can be recomputed using tracked repository files alone. The latest snapshot and dataset identity must match the exact `hotlines.json` bytes or the build fails. On bootstrap, trusted-base CI requires the base to contain neither a registry nor snapshot files, then requires exactly one zero-delta baseline whose complete snapshot and dataset hash derive from the trusted base's exact `hotlines.json` bytes. Later changes must preserve the trusted registry prefix and its snapshots byte-for-byte.

Append a reviewed release with `cd web && npm run release:dataset:candidate -- --id <lowercase-slug> --date <YYYY-MM-DD> --title <title> --summary <summary>`. All arguments are required. The command validates the existing chain before writing, refuses existing targets, creates the complete snapshot, and computes the delta from consecutive snapshots. Ordinary builds never create candidates. Review both files together. PR CI compares the trusted base branch registry and snapshots: every prior release object must remain an unchanged prefix and every prior snapshot must remain byte-identical. Local verification supplies internal SHA-256 hash-chain consistency and tamper evidence, not a signature, publisher authentication, or external cryptographic anchor.

Objects are recursively key-sorted before record hashing. Arrays are preserved in source order: contact methods, sources, languages, and other arrays may carry display, priority, or provenance meaning. Registry, snapshot, change, feed, and relevant generated-artifact ordering uses portable JavaScript UTF-16 code-unit comparison and never locale collation; BMP/non-BMP fixtures pin the behavior. Builds do not consult Git, GitHub, the network, filesystem enumeration order, locale, untracked files, wall clock, or subscriber/activity data for release history. Only the PR append-only verifier reads the explicitly supplied trusted base Git ref.

Public deterministic endpoints are `/release/v1/changes.json`, `/release/v1/changes/latest.json`, `/feeds/releases.json` (JSON Feed 1.1), `/feeds/releases.rss` (RSS 2.0), and `/feeds/releases.atom` (Atom 1.0). Feeds combine reviewed `releases.json` milestones and dataset-registry releases, newest first. Same-date ties sort by entry kind (`dataset`, then `milestone`) and stable source ID using UTF-16 code-unit order. Dates are represented at `00:00:00Z`; no build time is substituted. Stable entry IDs live under `https://worldhotlines.org/releases/{kind}/{id}`.

Change artifacts publish stable hotline IDs, country codes/names, change types, sorted changed top-level field names, and counts only. They never publish raw before/after hotline values. Record additions, removals, content modifications, country moves, and country-name metadata changes are distinct. A pure move has no misleading empty `changed_fields`; a move with record-content edits includes only those edited fields. Country summaries count moves as `moved_out` and `moved_in`, not as removals/modifications. Their per-kind sums equal the matching global counts; `total_changes` is record changes plus country metadata changes.
