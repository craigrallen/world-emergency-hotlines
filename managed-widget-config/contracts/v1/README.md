# Managed widget configuration v1 — static design contract only

This directory is a deterministic, **STATIC/SYNTHETIC** reference contract. It is not a hosted configuration, signing, ownership-verification, write, telemetry, billing, pricing, delivery, support, or SLA service. The key and every identity are test-only `.invalid` fixtures; trusting them in production is unsafe. The free public widget, API, and data remain keyless and unchanged.

`config.schema.json` closes the organization-facing policy surface. The five safety disclosures are fixed to `required_visible`: a configuration cannot remove or obscure emergency context, provenance, verification uncertainty, correction links, or the non-real-time limitation. Category filters are a closed, sorted enum drift-checked against the generated published category artifact. Channels are the sorted subset the current widget can select: `chat`, `phone`, and `text`; email is deliberately unsupported. Provider payment or status is not an input and must never affect ranking or verification.

`envelope.schema.json` describes the Ed25519 envelope. Signing bytes are UTF-8 `world-emergency-hotlines:managed-widget-config:v1`, LF, canonical protected JSON, LF, canonical payload JSON. Canonical JSON recursively sorts object keys and allows only JSON strings, booleans, null, safe integers, arrays, and plain objects. Base64url is unpadded and canonical. The protected audience contains both organization and project, must equal the payload tenant, and is independently compared with the verifier's expected organization and project. Domain matching is an additional check, never a substitute for tenant binding.

Verifiers fail closed on unknown fields, key, purpose, audience, HTTPS domain, time window (maximum 24 hours), signature, schema, replayed/stale revision, incomplete history, or unapproved rollback. Revision 1 is an explicit synthetic bootstrap identity. Every later material transition creates a new immutable identity from a domain-separated SHA-256 digest of the complete canonical successor content except `config_id`, after all mutations are complete, at the next contiguous revision and names the exact current head as predecessor. Complete-history validation recomputes those transition-derived identities. The published Draft 2020-12 schemas independently enforce all practical single-document structural and conditional constraints, including lifecycle percentages, rollback null pairing, and the minimum revision for a rollback. JSON Schema cannot express canonical array ordering, arithmetic equality between revision fields, content-derived identity, complete-history transitions, cryptographic verification, or one-use authorization. Those semantic checks require the reference verifier (or an equivalent implementation); an ordinary JSON Schema validator alone is not sufficient. The local AJV parity harness adds test-only keywords to compare these runtime-only invariants and does not imply that generic validators enforce them.

The local `model.mjs` and tests exercise creation/signing, preview, deterministic staged assignment, activation, retirement, rollback, and negative verification. Rollout is atomic: an installation uses one fully verified revision or the last verified revision; partial/invalid content is never merged. Staged percentages are 1 through 99; draft/retired are 0 and active is 100. Assignment compares the first unsigned 64 bits of a domain-separated SHA-256 digest with `floor(2^64 * percentage / 100)`, avoiding modulo bias and separating salt from installation token.

History is one ordered chain with contiguous increasing revisions, unique config identities, exact immediate-predecessor links, invariant tenant/domains/version pins, valid lifecycle paths, and a single last element as head. Rollback is itself a new active revision: it links to the current head and restores presentation, filters, safety copy, and rollout salt only from that head's immediate predecessor (`history.at(-2)`). The verifier accepts only an authorization ID and the trusted synthetic store, derives the expected tenant/current/target context itself, and requires the store's single atomic `consumeOnce` operation to return true after schema, history, signature, and time checks pass. Pre-registered strict plain-data records bind the authorization ID, organization, project, exact current and target identities, canonical not-before and expiry timestamps, and consumed state.

The local in-memory authorization store is a deterministic contract harness only. Its one-use behavior is confined to one harness instance and does not enforce anything across processes or restarts. A future implementation requires authenticated authorization issuance plus durable, transactional atomic consumption across processes and restarts; this static contract provides neither production authorization nor secrets or services.

Installation tokens in these fixtures are deliberately non-user synthetic strings. A future service must use random pseudonymous technical installation identity only and must never accept or store a user identity, IP address, crisis query, country, locality, category, hotline selection, path, referrer, or behavioural data.

The proposed dynamic URL in `openapi.json` is under `.invalid` and deliberately distinct from this static publication path. No dynamic route exists. Published files support only GET/HEAD/OPTIONS; writes and unknown files are 404.
