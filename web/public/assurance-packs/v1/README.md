# Data assurance pack v1 — STATIC/SYNTHETIC CONTRACT, NOT A SERVICE

This directory defines a deterministic, read-only assurance-pack document for a bounded set of canonical records. The example identity uses `.invalid`; it is not a customer/provider export, a current product offer, or evidence of a live assurance operation.

The pack uses a byte-pinned, internally validated synthetic upstream-release fixture with release ID `sha256:da1a06c5b11b20fc76afa269c324ab869293cdd67d232cf62f05724dc1fc124a`. The fixture exercises the repository's trusted-release parsing and identity-recomputation semantics, and the pack pins selected artifacts to exact entries in its synthetic index. The retained bytes and their internally valid identity do not establish where they were acquired, who published them, whether they were deployed, or any association with a commit, branch, current release, live release, or historical release.

The pack also pins exact canonical dataset identity, stable record membership, country/category coverage, evidence/reviewer summaries, uncertainty, and explicit deprecation/replacement state. It deliberately contains no phone/contact values, source locators, crisis queries, selections, users, identifiers, IPs, referrers, telemetry, pricing, billing, credentials, outreach, or security/SLA claims.

Provider claims are untrusted inputs. A separately supplied, fail-closed synthetic trust policy binds each allowed source ID to its record, source kind, locator hash, and authorized submitter; it separately binds authorized independent reviewer identities, roles, and decisions. The evidence input and derived pack both carry a closed `trust_policy` pin containing the policy's declared `policy_identity` and `sha256:<digest>` of the exact retained trust-policy fixture bytes (including whitespace and final newline). Both values are checked against the separately supplied parsed policy and bytes. Evidence cannot invent or relabel that authority, provider submitters cannot act as reviewers, and provider claims stay `pending` or `rejected`. Derivation and validation happen locally in `assurance-packs/model.mjs`; there is no ingestion, administration, persistence, or write route.

`assurance-pack.schema.json` is a closed Draft 2020-12 schema. It encodes per-record lifecycle/replacement nullability and evidence/uncertainty branches. Its `x-runtime-invariants` annotation lists cross-record, aggregate, and canonical-order checks that portable JSON Schema cannot express here. Consumers must validate with both the schema and the runtime validator in `assurance-packs/model.mjs`; neither check alone is sufficient. `assurance-pack.synthetic.json` is deterministically derived from conspicuously synthetic evidence and trust-policy fixtures and checked against the exact canonical `hotlines.json` bytes plus byte-pinned synthetic release/index fixtures. `dataset_version` is `sha256:<digest>` over those exact canonical bytes—not parsed records, selected membership, or release metadata—and must equal the evidence input, derived pack, and assessed release descriptor. SHA-256 values detect byte mismatch against retained bytes; they do not prove acquisition channel, publisher identity, deployment, provenance, freshness, or current/live/historical assurance.

Generation rejects symlinked dependencies, uses repeated digest-stable `O_NOFOLLOW` reads, pins device, inode, size, and high-resolution modification/change timestamps where the platform supplies them, and reopens and rereads every derivation dependency immediately before atomic publication to require the same metadata and exact bytes. These checks detect replacement and ordinary in-place mutation, including same-inode/same-size changes, but filesystem checks are not a transactional snapshot: a hostile concurrent writer may still exploit residual TOCTOU windows or unusual filesystem semantics. Generation therefore assumes controlled single-writer inputs.

The public crisis information and static API remain free. Public access does not grant reuse rights: this repository currently has no license, so permission must be confirmed before production reuse.
